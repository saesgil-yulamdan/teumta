# Route 데이터 구성 및 추천 기준

우회 코스를 어떤 기준으로 만들고 무엇을 후보에서 빼는지 정한다.

> 절 번호는 [api-spec.md](./api-spec.md)와 서버 코드 주석이 참조한다. **§6·§9·§13 번호는 유지한다.**

---

## 1. 코스는 두 종류다

| | 실시간 생성 | 저장형(큐레이션) |
|---|---|---|
| 만드는 시점 | 요청할 때마다 | 관리자가 미리 등록 |
| 장소 출처 | TourAPI/TMAP 실시간 조회 | 내부 `Place` |
| 저장 | 안 함 | `Route` / `RouteStop` |
| 범위 | **전국** | 적재된 지역(현재 종로구) |
| API | `GET /api/courses` | `GET /api/places/:placeId/routes`, `GET /api/routes/:routeId` |

**커버리지는 실시간 생성이 책임진다.** 저장형은 사람이 검수한 품질 사례로 남긴다.
아래 기준은 두 방식에 공통으로 적용하되, 저장 관련 항목은 저장형에만 해당한다.

---

## 2. 저장형 데이터 구조

**Route** — `mainPlaceId`(기준 관광지) · `name` · `description` ·
`estimatedTotalDurationMinutes` · `estimatedTotalDistanceMeters` ·
복귀 구간 `returnTravelMinutes` / `returnDistanceMeters` / `returnPath`

**RouteStop** — `routeId` · `placeId` · `stopOrder` · `stayMinutes` ·
`estimatedTravelMinutesFromPrevious` · `estimatedDistanceMetersFromPrevious` · `pathFromPrevious`

첫 RouteStop의 "이전 장소"는 `Route.mainPlace`다. `@@unique([routeId, stopOrder])`로 순서 중복을 막는다.

```
mainPlace → stop 1 → stop 2 → stop 3 → (복귀) mainPlace
```

---

## 3. 외부 데이터와 내부 Place의 구분

TourAPI로 조회한 관광정보(장소명·주소·좌표·이미지)를 **`Place`에 그대로 적재하지 않는다**(공모전 데이터 활용 기준).
따라서 실시간 조회 결과를 `RouteStop`에 자동 연결하지 않는다.

저장형 Route의 `RouteStop.placeId`는 팀이 직접 관리하는 내부 `Place.id`만 참조한다.
어떤 장소를 저장형 코스에 계속 쓰려면 내부 Place 관리 기준에 따라 별도로 등록한다.

---

## 4. 구성 원칙

- 기준 관광지(`mainPlace`)가 명확할 것
- 정류지 1곳 이상
- 좌표가 있어 TMAP 보행 경로 계산이 가능할 것
- 같은 코스 안에서 방문 순서가 중복되지 않을 것
- 사용자가 선택한 제한시간 안에 복귀까지 끝날 것

---

## 5. 정류지 선정 기준

**필수** — 좌표 존재 · mainPlace에서 걸어갈 수 있는 거리 · 실제 방문 가능한 장소.
저장형이면 내부 `Place`에 등록되어 있을 것.

**고려** — 운영시간 · 기본 권장 체류시간 · 장소 유형 · 태그 · mainPlace와의 거리 · 다른 정류지와의 위치 관계.

현재 `Place`에는 `openingTime`·`closingTime`만 있고 요일별 운영시간·휴무일 구조가 없다.
저장된 범위 안에서 확인 가능한 수준으로만 판단한다.

---

## 6. 권장 체류시간 기준

```
Place.recommendedDuration   장소 자체의 기본 권장 체류시간
RouteStop.stayMinutes       이 코스에서 실제로 적용하는 체류시간
```

**같은 장소라도 코스 제한시간에 따라 체류시간을 다르게 준다.** 기본값이 40분인 장소도
30분 코스에서는 20분으로 줄일 수 있다. 그렇게 하지 않으면 짧은 코스가 하나도 만들어지지 않는다
(가장 가까운 곳도 왕복 14분 + 체류 40분 = 54분).

**최소 체류시간은 지킨다(15분).** 지나치게 줄이면 방문 자체가 의미를 잃는다.

실시간 생성은 TourAPI 분류코드로 기본값을 정한다 — 문화시설(14) 40분 · 쇼핑(38) 30분 · 음식점(39) 40분 · 그 외 30분.
**공식 통계가 없는 팀 합의값**이므로 근거가 생기면 보정한다.

---

## 7. 30 / 60 / 90분 기준

| 짧은 코스 | 기본 코스 | 여유 코스 |
|---|---|---|
| 30분 | 60분 | 90분 |

"정확히 그만큼 걸린다"가 아니라 **사용자가 허용하는 최대 이용시간**이다.

```
총 소요시간 = mainPlace → 첫 정류지 이동
            + 정류지별 체류시간
            + 정류지 사이 이동시간
            + 복귀 구간 이동시간
```

총 소요시간이 선택 시간을 넘는 코스는 후보에서 뺀다(60분 선택 시 52분 → 포함, 67분 → 제외).

---

## 8. 방문 순서

접근성 · 정류지 사이 실제 보행시간 · 불필요한 왕복 최소화 · 전체 이동거리 · 운영시간을 함께 본다.
저장형은 `stopOrder` 오름차순으로 조회·반환한다.

---

## 9. TMAP 경로 계산과 복귀 구간

경로 계산에는 **장소의 고정 좌표만** 사용한다. 사용자 GPS는 서버에도 TMAP 요청에도 들어가지 않는다
([location-privacy.md](./location-privacy.md)). `pathFromPrevious`는 지도 폴리라인용 고정 경로이며
사용자의 이동 기록이 아니다.

**복귀 구간 저장 방식은 확정됐다**(초안의 "추후 확정" 해소).
`RouteStop`의 경로 필드는 전부 "이전 장소 → 현재 정류지" 기준이라 마지막 정류지에서 mainPlace로
돌아오는 구간을 담을 자리가 없었다. `Route`에 3개 필드를 두는 것으로 정했다.

```prisma
returnTravelMinutes  Int?
returnDistanceMeters Int?
returnPath           Json?
```

전부 nullable — 기존 행은 복귀 미포함으로 해석한다. `RouteStop`에 mainPlace를 가상 행으로 넣는 대안은
기존 조회 응답에서 "마지막 stop이 방문지인지 복귀인지" 구분이 안 되어 탈락했다.

⚠️ 실시간 생성 코스(`GET /api/courses`)의 응답에는 **아직 경로 도형이 없다.**
앱 지도는 정류지 점을 직선으로 잇고 있다. 서버가 이미 TMAP 실측 호출을 하고 있으므로
추가 호출 없이 응답에 실을 수 있다 — 명세 변경이 필요한 항목.

---

## 10. 소요시간 검증

저장형은 등록 시점에 계산한 값을 저장하고, 조회 때 TMAP을 다시 부르지 않는다(호출 한도·응답속도).

실시간 생성은 목적지↔정류지를 실측하고, 정류지 사이는 추정으로 후보를 좁힌 뒤
**반환할 코스에 한해 실측**한다. 실측 후 시간이 늘어 제한시간을 넘기면 그 코스는 뺀다.
전 구간 실측이 끝난 코스만 `verified: true`로 표시한다.

---

## 11. 필터링

**1차** — 기준 관광지가 맞는지 · 선택 시간 조건 · 정류지 데이터 정상 여부 · 운영시간 정보가 있으면 방문 가능 시각인지

**최종** — TMAP 계산 성공 여부 · 재계산한 총 소요시간이 선택 시간 이하인지 · 복귀 가능 여부 ·
이용 불가로 확인된 장소가 없는지

조건을 만족하지 않는 코스는 후보에서 제외한다.

---

## 12. 정렬

**남는 시간이 적은 순 → 같으면 정류지가 많은 순.** 로컬 장소를 더 들르는 편이 분산 효과가 크다.

점수 기반 모델은 쓰지 않는다. 개별 정류지의 실시간 혼잡도를 정렬에 넣을지는 SK 장소별 조회 범위를 확인한 뒤 정한다.

---

## 13. 데이터 누락 및 예외 처리

| 상황 | 처리 |
|---|---|
| 좌표 없음 | 경로 계산 불가 — 정류지로 쓰지 않는다. `Number(null) === 0`이므로 `0`도 무효 좌표로 본다 |
| 체류시간 없음 | 분류별 기본값 적용(§6) |
| 운영시간 없음 | 확인 가능한 범위에서만 판단. 별도 추천 정책 필요 |
| 휴무일 | 현재 스키마로 판단 불가 |
| **TMAP 계산 실패** | **경로가 검증되지 않은 코스는 추천 후보로 쓰지 않는다.** 저장형은 미완성 상태로 저장하지 않고(전체 실패), 실시간은 그 후보를 뺀다 |
| 선택 시간 내 코스 없음 | 없음을 안내하고 더 긴 시간(30→60→90분)을 권한다 |
| 쓸 내부 Place 없음 | 외부 조회 결과를 임의로 `RouteStop`에 연결하지 않는다(§3) |

## 14. Route와 Trip

```
Route      방문 장소·순서·예상 시간의 정의
Trip       사용자가 특정 Route를 이용하는 단위(status, startedAt, endedAt)
TripEvent  Trip 수준의 이벤트 기록
```

`TripEventType` enum에는 6종이 있지만 **서버가 허용하는 것은 3종뿐**이다 —
`TRIP_STARTED` / `TRIP_COMPLETED` / `TRIP_CANCELLED`. 각각 Trip 상태와 시각을 함께 갱신한다.

`PLACE_ARRIVED`·`PLACE_LEFT`·`MAIN_PLACE_RETURNED`는 **의도적으로 열지 않는다.**
서버에 방문 장소·시각이 남으면 위치정보 정책이 깨진다. 도착·출발·복귀 판정은 전부 단말 local state에서 한다.
`TripEvent`에 사용자 좌표 필드를 두지 않으며 `metadata`에도 위치를 넣지 않는다.

> 현재 앱은 Trip/TripEvent API를 호출하지 않는다. 배경과 재론 조건은 [team-todo.md](./team-todo.md) "확정 정책" 참조.

---

## 15. 미결정

- 저장형 코스에 넣을 내부 Place 선정·등록 절차
- 장소 유형별 기본 `recommendedDuration` 근거 확보
- 코스 소요시간에 여유시간을 별도로 둘지
- 운영시간을 확인할 수 없는 장소의 추천 정책
- 요일별 운영시간·휴무일 데이터 확보 방식
- 실시간 코스 응답에 경로 도형을 포함할지(§9)
