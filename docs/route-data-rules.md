# 실시간 코스 생성 규칙

현재 앱은 DB 저장형 Route가 아니라 `GET /api/courses`의 요청 시점 생성 코스만 사용합니다.

## 입력과 형태

- 목적지 식별자: TourAPI `contentId` 또는 TMAP `poiId` 중 하나
- 허용 시간: 서버 10~240분, 앱 선택지 30/60/90분
- 코스: 목적지 → 최대 3개 정류지 → 원 목적지 복귀
- 최대 3개 코스 반환
- 사용자 GPS는 입력하지 않으며 장소 고정 좌표끼리만 경로 계산

## 후보와 체류시간

주변 문화시설(14), 쇼핑(38), 음식점(39)과 진행 중·예정 행사를 후보로 사용합니다. 조합 폭발과 외부 API 쿼터를 막기 위해 분류 균형을 고려한 최대 10곳만 계획에 사용합니다.

기본 체류시간은 문화시설 40분, 쇼핑 30분, 음식점 40분, 행사/그 외 30분이며 최소 15분까지 줄일 수 있습니다. 이는 공식 통계가 아닌 제품 정책입니다.

```text
총 시간 = 모든 이동시간 + 모든 체류시간 + 마지막 정류지의 복귀시간
```

총 시간이 사용자의 허용 시간을 넘으면 제외합니다.

## 이용 가능 여부

서버는 상위 계획에서 고유 TourAPI 장소 최대 5곳의 `detailIntro2`를 동시 3개씩 조회합니다. 예상 도착 시각은 현재 KST 시각에 앞선 구간의 이동·체류시간을 더해 계산합니다.

- 명확한 정기 휴무 또는 오늘 휴무: 제외
- 명확한 운영시간 밖: 제외
- 명확한 브레이크타임: 제외
- 운영정보 없음, 비정형 문구, 해석 불가: `unknown`으로 유지해 자동 제외하지 않음
- 행사: 행사 날짜 조회에서 이미 기간 필터를 거치므로 운영문구 조회 대상에서 제외

외부 운영정보 자체가 틀리거나 임시휴무가 늦게 반영될 수 있으므로 100% 보장은 아닙니다. 진행 화면은 현재 정류지 운영정보를 다시 확인하고 대체 코스를 요청할 수 있습니다.

## 경로 검증

목적지↔후보 측정값을 재사용하고, 정류지 사이는 직선거리 보정치로 우선 계획합니다. 정렬된 상위 계획 최대 8개만 TMAP으로 모든 구간을 실측합니다. 하나라도 실패하거나 실측 후 허용 시간을 넘으면 반환하지 않습니다. 반환 코스는 `verified: true`입니다.

## 정렬

현재 코드는 단순한 “남는 시간 오름차순”이 아니라 가중 점수를 사용합니다. 다음 요소를 함께 반영합니다.

- 허용 시간을 얼마나 알차게 쓰는지
- 정류지 수와 장소 유형의 다양성
- 전체 보행거리
- `variant`에 따른 안정적인 다양화

동점은 총 시간, 정류지 수, 코스 키로 안정적으로 결정합니다. 실시간 혼잡도는 개별 정류지 정렬 점수에 넣지 않습니다.

## 캐시

- 목적지↔주변 후보 TMAP 측정: 서버 5분
- 완성 코스: 서버 2분, 최대 300건
- 동일 코스 요청: 모바일 30초, 최대 40건이며 진행 중 Promise도 공유

날짜가 캐시 키에 들어가 휴무 판정이 다른 KST 날짜로 넘어가지 않습니다.

## 저장형 코드

Prisma `Route`, `RouteStop`, `Trip`, `TripEvent`와 관련 서비스는 과거 구현 보존용입니다. 현재 공개 라우터와 모바일 플로우에서는 사용하지 않습니다.
