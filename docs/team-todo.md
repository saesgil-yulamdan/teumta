### 현재 구조 (이 결정으로 바뀌는 것 없음)

- 서버는 `TRIP_STARTED`/`TRIP_COMPLETED`/`TRIP_CANCELLED` 3종만 허용

- 앱은 Trip API를 호출하지 않는다. 코스 진행 상태는 단말 local state

### 왜 열지 않나 — 기존 문서 4건을 그대로 지키기 위해

1. `location-privacy.md` §1 — **"서버가 모르는 것: 사용자의 현재 위치, 이동 경로, 위치 history,
   도착/방문 시각·장소"**
2. `location-privacy.md` §2 — **"현재 Trip/TripEvent를 사용하는 API/코드는 없다(진행 상태는 서버에
   저장되지 않음)"**
3. `app-store-listing.md` — App Privacy를 **"Data Not Collected"** 로 신고. 전 항목 해당 없음을
   2026-08-15에 확인해 근거를 문서화해둔 상태
4. 요강 FAQ의 **위치기반서비스사업자 비신고 요건** 서술 — 근거가 3과 같다

`PLACE_ARRIVED + placeId + occurredAt`을 허용하면 1·2가 곧바로 거짓이 되고 3·4의 근거를 다시 세워야 한다.
`Trip`에 `userId`도 `deviceId`도 없어 익명이므로 법적으로는 통과할 여지가 있지만,
**마감 5주 전에 개인정보 신고 근거를 재검토하는 비용이 지표 하나의 값어치보다 크다.**

앞선 항목(TOUR 목적지 실시간 혼잡도, `404 CONGESTION_DATA_NOT_FOUND` 안내, 집중률 예측 화면,

### 1. 우회 제안 강조 기준 — 미구현

`places/[id].tsx`의 "틈타 코스 보기" CTA가 **혼잡도와 무관하게 항상 같은 모양**이다.
`congestion-rules.md` §5의 확정 기준대로 `CROWDED` 이상일 때 강조해야 한다.

- `CROWDED`/`VERY_CROWDED` → CTA 강조 + "지금 붐빕니다. 근처 조용한 곳으로 가볼까요?" 류 안내
- 그 미만 → 현재 모양 유지
- 실시간 혼잡도가 없는 장소(`404`)는 집중률 예측값으로 대체하지 않는다 — 둘은 다른 지표다

**심사에서 이 화면이 서비스 프레임 그 자체다.** 혼잡을 감지해 분산을 제안하는 순간이 눈에 보여야 한다.

### 2. 코스 지도 경로선 — PR 대기

경로가 둥근 점으로 그려져 장소 마커와 구분되지 않던 문제. 파선 + 흰 밑선으로 교체
(브랜치 `fix/course-map-route-line`).

### 3. 코스 화면 실데이터 확인 — 코스 입력 후

코스 목록/상세는 `GET /api/places/:placeId/routes`, `GET /api/routes/:routeId` 연동 완료.
DB에 코스가 들어간 뒤 **실제 좌표로 지도·타임라인이 맞게 그려지는지** 한 번 확인한다
(`stops[].pathFromPrevious` 폴리라인, 복귀 구간 `Route.returnPath`).

### 상시 원칙

- 사용자 GPS를 서버로 보내지 않는다(서버 API에 좌표 파라미터 자체가 없음)

- 검색 자동완성 금지(버튼 또는 500ms+ debounce) — 외부 API 쿼터

## 📊 데이터로직 담당

판단 기준 문서 정리 완료 — [congestion-rules](./congestion-rules.md)(우회 트리거 `CROWDED` 이상,
KTO/SK 역할 구분, KTO 적재 규칙), [route-data-rules](./route-data-rules.md)(코스 구성·체류시간·예외 처리).

### 1. 분산 효과 지표 — 공급 지표로 확정

행동 측정을 하지 않기로 했으므로, **서버 DB에 이미 있는 값만** 집계한다. 전부 실측이라 추정·가정이 없다.

| 지표 | 계산 | 무엇을 말하나 |
|---|---|---|
| 우회 코스 수 | `Route` 건수 | 공급한 분산 경로의 양 |
| 코스 보유 관광지 수 | `Route.mainPlaceId` distinct | 혼잡 관광지 중 대안이 준비된 곳 |
| 분산 대상 로컬 장소 수 | `RouteStop.placeId` distinct (`LOCAL_PLACE`) | 발걸음이 향할 상권의 규모 |
| 관광지별 우회 용량 | 관광지별 코스 수 · 평균 정류지 수 | **대안이 부족한 관광지**를 찾는 용도 |
| 혼잡 감지 커버리지 | KTO 집중률 매칭 수 / 대상 수 | 분산을 제안할 수 있는 범위 |
| 로컬 장소 큐레이션 완료율 | 태그·설명·추천 체류시간이 채워진 비율 | 코스에 넣을 수 있는 장소의 품질 |

**Never Fake Analytics 유지** — "예상 분산 인원" 같은 추정 지표는 만들지 않는다.
사용자 수·방문 수를 시사하는 어떤 수치도 이 화면에 넣지 않는다.

### 2. 발표에서 분산 효과는 "측정 계획"으로 서술

실사용 행동지표(로컬 도착률·복귀율)는 **의도적으로 수집하지 않는다**는 사실 자체를 강점으로 쓴다.

- 현재: 서비스가 확보한 **분산 용량**을 실측으로 제시(위 표)
- 향후: 행동지표가 필요해지면 **개인정보 영향 검토를 먼저 거친 뒤** 익명 집계로 확장하겠다는 계획을 제시
- 근거: `location-privacy.md`의 단말 내부 처리 구조 + 스토어 App Privacy "Data Not Collected" 신고

"측정할 수 있는데 안 했다"가 아니라 **"측정하지 않도록 설계했다"**가 논지다.

### 3. 공모전 스토리

"관광객을 줄이지 않고 발걸음과 지갑을 옆 골목으로 옮긴다" 프레임으로 기능설명서 골격.
해시태그별 기능 흐름도가 제출 필수 항목이다.

### 4. 위치정보 아키텍처를 강점으로 서술

단말 내부 처리 + 서버 미전송 구조가 요강 FAQ의 위치기반서비스사업자 **비신고 요건에 그대로 부합**한다.
확정하려면 위치정보지원센터(lbsc.kr) 사전 검토 권장.
