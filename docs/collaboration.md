## 3. 데이터 인계 규칙

| 성격 | 예시 | 방식 |
|------|------|------|
| 정적/준정적 | 관광지 정보 | **DB 테이블** — B가 `tourApiContentId` 기준 upsert, A는 read |
| 예측/축적형 | 집중률 예측 | **DB 테이블** — B가 `Congestion(type=PREDICTED)` 적재, A가 조회 API |
| 휘발성/실시간 | 실시간 혼잡도, 이동시간 | **서비스 함수** — 저장하지 않고 호출 (필요 시 짧은 TTL 캐시) |

원칙: **B는 A의 테이블 구조에 최대한 의존하지 않는다.** 실시간·파생 데이터는 "입력 → DTO 출력" 순수 함수로 넘긴다.

## 4. 협업 규칙

### 4.1 Git

- `main` **직접 push 금지**, 항상 PR
- 브랜치: `feature/<영역>-<내용>` / `fix/...` / `docs/...`
- 작업 전 `main` 최신화

### 4.2 PR

- 제목은 Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`)
- 본문에 **무엇을 / 왜 / 영향 범위**
- **스키마 변경 또는 API 명세 변경이 포함되면 상대방 리뷰 필수.** 그 외 자기 영역 단독 변경은 셀프 머지 허용

### 4.3 스키마 변경 (충돌 예방 핵심)

- `schema.prisma` 변경 권한은 **A가 오너**
- B가 저장 구조가 필요하면 → **이슈/메시지로 A에게 요청**, A가 마이그레이션 생성
- 마이그레이션 파일은 반드시 커밋해 공유 (`npx prisma migrate dev --name <name>`)
- 병합 후 각자 `npm run db:generate` — 잊으면 새 필드가 클라이언트에 없어 타입 오류가 난다
  (`postinstall`에 걸어뒀으므로 `npm install`로도 해소)

### 4.4 API 명세

- 정본은 [api-spec.md](./api-spec.md). **명세를 먼저 고치고 → 구현**(spec-first)
- 응답 봉투 `{ success, data, error }` · camelCase · ISO8601 · 좌표 `number` · `tags` 평탄화
- 실패 응답은 `{ code, message }` — 클라이언트 분기용 `error.code`를 함께 준다

### 4.5 코드 컨벤션

- 레이어: `routes → controllers → services → prisma`
- 외부 연동은 `external/`에 격리하고 컨트롤러는 얇게
- 환경변수는 `src/config/env.ts`의 Zod 스키마에 추가
- **비밀 키는 `.env`에만.** 새 변수는 `.env.example`에 키 이름만 추가. 문서·저장소에 값 금지

## 5. 커뮤니케이션

- **경계에 걸치는 변경**(스키마, API 명세, 서비스 함수 시그니처)은 반드시 사전 공유
- 상대방 영역을 대신 진행해야 할 상황이면 **먼저 기한을 정해 공유하고**, 그 기한이 지난 뒤에 움직인다
- 막히면 빨리 공유 — 스키마·명세 의존이 서로의 진행을 막는다
