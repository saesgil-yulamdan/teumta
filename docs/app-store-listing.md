# App Store Connect 등록 문구

> 제출 시 App Store Connect의 각 칸에 그대로 붙여 넣는다.
> **앱에 실제로 있는 기능만 쓴다** — 없는 기능을 적으면 심사에서 리젝 사유가 되고,
> 실제 동작과 다른 설명은 이용자 신뢰 문제이기도 하다.

## 부제 (Subtitle, 30자 이내)

```
인기 관광지와 로컬을 잇는 우회 여행
```

## 프로모션 텍스트 (Promotional Text, 170자 이내)

기능을 나열하지 않고 브랜드 톤으로 쓴다. **심사 없이 언제든 바꿀 수 있는 칸**이라
계절·이벤트에 맞춰 교체하기 좋다.

```
붐비는 곳을 비켜, 여행은 그대로. 가려던 곳이 붐빈다면 걸어서 가까운 곳부터 둘러보세요. 틈타가 내 시간에 맞는 로컬 코스와 돌아갈 순간을 함께 찾아드려요.
```

교체용 대안:

```
붐비는 순간에도 여행은 이어집니다. 가려던 곳이 붐빈다면, 걸어서 닿는 곳부터 둘러보세요. 틈타가 시간에 맞는 로컬 코스와 돌아갈 순간을 찾아드려요.
```

## 설명 (Description)

```
붐비는 관광지 앞에서, 걸어서 갈 수 있는 근처로

가고 싶었던 관광지에 도착했는데 사람이 너무 많다면 어떻게 하시나요?

한참을 기다리거나 발길을 돌리기 전에, 틈타보세요.

틈타는 관광지가 지금 얼마나 붐비는지 확인하고, 여유가 있는 만큼의 시간에 맞춰 걸어서 다녀올 수 있는 근처를 둘러보는 우회 코스를 만들어 드립니다. 실제 보행 경로로 계산하고, 원래 가려던 곳으로 언제 돌아오면 되는지까지 함께 보여드려요.

관광객이 한곳에 몰려 있는 사이, 걸어서 몇 분 거리의 미술관과 밥집, 작은 상점은 한산합니다. 틈타는 그 사이를 이어 여행이 끊기지 않게 합니다.

■ 지금 얼마나 붐비는지 확인
방문하려는 관광지의 실시간 혼잡도를 확인해보세요. (혼잡도 정보가 제공되는 관광지에 한해 표시됩니다)

■ 덜 붐비는 날 고르기
앞으로 30일간의 날짜별 관광지 집중률을 참고해 방문 날짜를 정할 수 있어요.

■ 시간에 맞춘 우회 코스
30분, 60분, 90분 — 쓸 수 있는 시간을 고르면 그 안에 다녀올 수 있는 코스를 만들어 드려요. 걷는 시간은 실제 보행 경로로 계산합니다.

■ 걸어서 닿는 로컬 장소
유명 관광지만 보고 지나쳤다면 몰랐을 근처의 문화시설, 밥집, 상점을 만나보세요.

■ 돌아갈 시간 안내
우회의 끝은 새로운 목적지가 아닙니다. 처음 가려던 곳으로 돌아갈 예상 시각을 코스와 함께 보여드리고, 알림을 허용하면 복귀 출발 5분 전에 알려드려요.

■ 로그인 없이, 위치는 기기 안에서만
회원가입이 필요 없습니다. 현재 위치는 도착 여부를 확인하는 데만 쓰이며 기기 밖으로 나가지 않습니다.

붐비는 곳을 피해 여행을 포기하는 대신,
그 사이의 틈을 새로운 여행으로 바꿔보세요.

틈타 — 붐비는 시간은 비켜가고, 여행은 그대로.

출처: ⓒ한국관광공사
```

리뷰어가 기능을 오해해 리젝하는 것을 막는 칸이다. 특히 **실시간 혼잡도가 일부 장소에만 표시되는 것**을

```
Teumta helps travelers avoid overcrowded tourist attractions in South Korea.
When a destination is busy, the app suggests nearby local places you can walk to
within your available time, and tells you when to head back.

NO ACCOUNT NEEDED
The app has no sign-up or login. All features are available immediately.

HOW TO TEST
1. Open the app and tap the search field.
2. Search for "경복궁" (Gyeongbokgung Palace) or "해운대해수욕장" (Haeundae Beach).
   Note: search covers South Korean tourist attractions only, so Korean keywords
   work best. Tap the search button (there is no auto-complete, by design, to
   limit external API usage).
3. Tap a result to see the destination detail: real-time crowd level and a
   30-day daily concentration forecast.
4. Tap "틈타 코스 보기" (View courses) and choose 30 / 60 / 90 minutes.
   The server generates walking courses in real time; this takes a few seconds.
5. Tap a course, then "이 코스로 출발하기" (Start this course) to see the map and
   progress screen.

ABOUT REAL-TIME CROWD LEVELS
Real-time crowd data is provided by a third-party service that covers only a
subset of places. When a place is not covered, the app shows "이 장소는 실시간
혼잡도를 제공하지 않아요" (real-time crowd level is not available here). This is
expected behavior, not an error. The 30-day forecast is available nationwide.

LOCATION PERMISSION
Location is optional. Search, crowd levels, forecasts and course generation all
work without granting it. Location is only used during an active course to
detect arrival at a stop, and it is processed on the device only — it is never
sent to our servers. We do not use background location.

LOCAL NOTIFICATIONS
When a course starts, the app asks for notification permission and schedules a
local reminder to head back (5 minutes before the return leg). Notifications
are optional and scheduled entirely on the device — the app never creates push
tokens and has no remote push capability. Declining the permission only skips
the reminder; everything else works.

DATA SOURCES
Tourism data is provided by the Korea Tourism Organization (public open data).
Walking routes and real-time crowd levels come from SK Telecom open APIs.
Attribution "출처: ⓒ한국관광공사" (Source: © Korea Tourism Organization) is shown
on screens that display this data.

PRIVACY
No user accounts, no analytics, no advertising identifiers. We do not collect
personal data. Saved places, course history and recent searches are stored on
the device only.
```

## 이전 문구에서 바꾼 점과 이유

| 바뀐 것 | 이유 |
|---|---|
| "기다리는 시간을 여행으로" → "붐비는 관광지 앞에서, 걸어서 갈 수 있는 근처로" | 서비스의 문제의식이 **시간 때우기**가 아니라 **한곳에 몰린 관광객을 주변으로 분산**하는 것이다. 대표 문구가 방향을 정한다 |
| 로컬 상권을 명시(문화시설·밥집·상점) | 우회 코스가 실제로 음식점·쇼핑·문화시설을 후보로 삼는다. 분산의 수혜자가 누구인지 드러난다 |
| **"골목" 표현 삭제 → "걸어서 갈 수 있는 근처"** | 실제 추천 결과는 골목이 아니다. 경복궁 주변은 국립현대미술관·세종문화회관 같은 대형 문화시설이 나오고, 성산일출봉처럼 골목이랄 게 없는 곳도 대상이다. "골목"은 서울 원도심으로 범위를 좁혀 전국 서비스라는 사실과 어긋난다 |
| "덜 붐비는 날 고르기" 항목 추가 | 30일 집중률 예측은 실제 기능인데 이전 문구에 빠져 있었다. 여행 **전** 단계의 분산이라 서사에도 맞는다 |
| "실제 보행 경로로 계산" 문구 추가 | 직선거리가 아니라 실제 도보 경로로 계산한다. 경쟁 앱과 구분되는 지점 |
| 혼잡도에 "제공되는 관광지에 한해" 단서 | 모든 관광지에 실시간 혼잡도가 있지 않다. 과장하면 리젝 사유가 된다 |
| **"복귀 전 알림" 문구 복원** (한때 미구현으로 삭제) | 2026-08-16 로컬 알림 구현 완료 — 코스 시작 시 복귀 출발 5분 전 알림 예약(예약·발송 전부 단말 내, 푸시 토큰 미생성). 예전 문구 "10분 전"이 아니라 **실제 동작대로 "복귀 출발 5분 전"** 으로 서술하고, 권한 선택 사항이므로 "알림을 허용하면" 단서를 붙였다 |
| 로그인 불필요·위치 미전송 명시 | 심사에서 유리하고, 우리 아키텍처의 실제 강점이다 |

## App Privacy(수집 데이터) 신고 근거

Apple 기준의 "수집(collect)"은 데이터를 기기 밖으로 보내 **요청을 실시간 처리하는 데 필요한 기간보다
오래 접근 가능하게 두는 것**이다. 전송 자체가 아니라 **보관**이 기준이다.

확인 결과(2026-08-15) 전 항목이 해당 없음이라 **"Data Not Collected"** 로 신고한다.

| 확인 항목 | 상태 |
|---|---|
| 분석·광고·크래시 SDK | 없음(Firebase/Sentry/Amplitude/AdMob 등 0개, `expo-updates`도 미설치) |
| 계정·기기 식별자·광고 식별자 | 없음(회원가입 자체가 없음) |
| 위치 전송 | 없음 — 서버 API에 좌표 파라미터가 존재하지 않음 |
| 서버로 가는 값 | 검색어·목적지 코드·가용 시간. 해당 요청 처리에만 쓰고 보관하지 않음 |
| 요청 본문 로깅 | 없음(`error.middleware`가 sanitized message만 기록) |
| 기기 저장 데이터 | 저장한 장소·코스 기록·최근 검색어(AsyncStorage) — 기기 밖으로 나가지 않음 |
| 알림 | 로컬 알림만(복귀 임박·혼잡 해소). 단말이 스스로 예약·발송, 푸시 토큰 미생성 |
| 제보·문의 | 외부 메일 앱에 제보 유형·공개 장소 정보·앱 버전·운영체제만 초안으로 전달. 사용자가 확인 후 직접 전송하며 위치·기기 ID는 포함하지 않음 |
| 추적(Tracking) | 없음 → ATT 팝업 불필요(`expo-tracking-transparency` 미설치) |

> 제보 메일은 선택적 고객 지원 요청이다. Apple의 optional disclosure 조건 충족 여부는 메일 앱의
> 발신자 표시와 실제 운영 방식을 포함해 제출 직전에 다시 확인한다. 조건을 모두 충족하지 못하면
> `Customer Support` 및 관련 연락처 데이터를 App Store Connect에 공개해야 한다.

### 이 신고를 반드시 다시 검토해야 하는 변경

- 크래시 리포팅·분석 도구 도입(Sentry, Firebase Analytics 등)
- **원격 푸시 알림 도입 시** — 푸시 토큰은 기기 식별자라 신고 대상이 된다(현재는 로컬 알림만이라 해당 없음)
- 서버에서 검색어·요청 내역을 로그로 축적
- **성과 분석을 위해 TripEvent를 실제로 기록하기 시작할 때** — 계정이 없어 개인 식별은 안 되지만
  사용 이력을 서버에 남기는 것이라 `Usage Data` 신고 대상이 될 수 있다
- **좌표 기반 "근처 관광지" 검색 도입 시**([api-spec 3.2](./api-spec.md)의 보류된 `?lat=&lng=` 확장안) —
  사용자 좌표가 서버로 가는 순간 `대략적인 위치`/`정확한 위치` 신고 대상이 되고,
  location-privacy.md의 "서버는 좌표를 입력으로 받지 않는다" 원칙도 함께 깨진다

> 참고: `대략적인 위치`(소수점 3자리 미만 좌표)는 **좌표를 뭉개서 보내도** 기기 밖으로 내보내
> 보관하면 신고 대상이다. 현재는 위치가 기기를 벗어나지 않고 IP로 위치를 추정하지도 않아 해당 없음.
> 지도의 내 위치 표시는 Apple MapKit이 기기 안에서 처리하므로 우리 수집이 아니다.
