# 분산 효과 지표 산정 기준

## 1. 문서 목적

틈타 서비스가 오버투어리즘 완화를 위해 어느 정도의 우회 선택지와 로컬 장소를 확보하고 있는지 확인할 수 있도록 성과 분석용 지표의 산정 기준을 정의한다.

현재 서비스는 사용자의 실제 이동 경로, 장소 도착 여부, 방문 시각 및 복귀 여부를 서버에 수집하지 않는다.

따라서 현재 단계에서는 사용자 행동을 추정한 지표가 아니라, 서버와 관리자 데이터에 근거한 **공급 지표**를 사용한다.

본 문서는 관리자 웹 `/analytics`에서 사용할 지표의 의미와 계산 범위를 통일하고, 같은 지표가 구현 위치에 따라 다르게 계산되는 것을 방지하는 것을 목적으로 한다.

관련 문서는 다음과 같다.

* [team-todo.md](./team-todo.md)
* [route-data-rules.md](./route-data-rules.md)
* [service-overview.md](./service-overview.md)

## 2. 기본 원칙

### 2.1 사용자 행동을 성과 지표로 만들지 않는다

현재 앱은 코스 진행 상태와 장소 도착 여부를 단말 내부에서 처리한다.

사용자 GPS와 이동 경로는 서버로 전송하거나 저장하지 않으며, 앱은 현재 Trip/TripEvent API를 사용하지 않는다.

따라서 다음과 같은 지표는 현재 제공하지 않는다.

* 실제 우회 선택자 수
* 우회 선택률
* 로컬 장소 실제 방문자 수
* 로컬 장소 도착률
* 원 관광지 복귀율
* 실제 분산 관광객 수
* 예상 분산 인원
* 사용자별 평균 우회시간

실제 측정 데이터가 없는 값을 추정하거나 임의의 가정으로 생성하지 않는다.

이를 **Never Fake Analytics** 원칙으로 유지한다.

### 2.2 현재 지표는 분산 효과 자체가 아니라 분산 공급 역량을 나타낸다

현재 성과 분석에서 보여주는 값은 다음과 같은 질문에 답하기 위한 지표이다.

```text
얼마나 많은 우회 코스를 준비했는가?
얼마나 많은 관광지에 대안을 준비했는가?
얼마나 다양한 로컬 장소를 분산 대상으로 확보했는가?
각 관광지에 몇 개의 대안이 존재하는가?
집중률 데이터를 어느 정도 연결할 수 있는가?
로컬 장소 큐레이션은 어느 정도 완료되었는가?
```

따라서 현재 지표를 실제 관광객 분산 성과 또는 실제 방문 증가량으로 해석하지 않는다.

### 2.3 저장형 코스만 공급 지표에 포함한다

모바일에서 사용하는 실시간 코스는 `GET /api/courses` 요청 시 생성되며 DB에 저장하지 않는다.

성과 분석의 Route 관련 지표는 관리자가 등록한 저장형 코스인 다음 데이터를 기준으로 계산한다.

```text
Route
RouteStop
Place
PlaceTag
```

실시간 생성 코스는 요청 후 저장되지 않으므로 Route 기반 공급 지표에 포함하지 않는다.

따라서 Route 관련 지표는 **전국 실시간 코스 생성 가능 범위**를 의미하는 것이 아니라, 현재 팀이 직접 등록하고 관리하는 **큐레이션된 저장형 우회 코스의 공급 현황**을 의미한다.

## 3. 지표 요약

| 지표             | 기본 계산                                        | 의미                         |
| -------------- | -------------------------------------------- | -------------------------- |
| 우회 코스 수        | `Route` 전체 건수                                | 등록된 저장형 분산 경로의 양           |
| 코스 보유 관광지 수    | `Route.mainPlaceId` distinct                 | 저장형 우회 대안이 준비된 관광지 수       |
| 분산 대상 로컬 장소 수  | `RouteStop.placeId` distinct + `LOCAL_PLACE` | 저장형 코스가 연결하는 고유 로컬 장소 수    |
| 관광지별 우회 용량     | 관광지별 코스 수 + 평균 정류지 수                         | 각 관광지가 확보한 우회 선택지의 규모      |
| 혼잡 감지 커버리지     | KTO 매칭 성공 대상 수 / KTO 전체 대상 수                 | 집중률 예측을 내부 장소와 연결할 수 있는 범위 |
| 로컬 장소 큐레이션 완료율 | 필수 큐레이션 완료 로컬 장소 / 전체 로컬 장소                  | 저장형 코스에 활용할 로컬 장소 데이터의 완성도 |

각 지표는 현재 데이터를 기준으로 계산하는 **snapshot 지표**이다.

Route 또는 Place가 추가·수정·삭제되면 값도 함께 변경된다.

현재 데이터 개수를 문서나 코드에 고정값으로 저장하지 않고 집계 시점의 데이터를 사용한다.

## 4. 우회 코스 수

### 정의

현재 DB에 등록되어 있는 저장형 `Route`의 전체 개수이다.

### 계산

```text
우회 코스 수
= COUNT(Route.id)
```

동일한 관광지에 30분, 60분, 90분 코스가 각각 등록되어 있다면 각각 별도의 Route이므로 각각 1개로 계산한다.

### 포함

* 관리자에 의해 DB에 등록된 저장형 Route

### 제외

* `GET /api/courses`에서 요청 시 생성되는 실시간 코스
* DB에 저장되지 않은 추천 결과

### 해석

이 지표는 실제 사용자가 몇 번 우회했는지를 나타내지 않는다.

현재 팀이 직접 등록해 둔 **저장형 분산 경로의 공급량**을 의미한다.

---

## 5. 코스 보유 관광지 수

### 정의

하나 이상의 저장형 Route가 연결되어 있는 기준 관광지의 고유 개수이다.

### 계산

```text
코스 보유 관광지 수
= COUNT(DISTINCT Route.mainPlaceId)
```

한 관광지에 Route가 여러 개 있어도 관광지 수는 1개로 계산한다.

예시는 다음과 같다.

```text
관광지 A
- 30분 Route
- 60분 Route
- 90분 Route

→ 우회 코스 수: 3
→ 코스 보유 관광지 수: 1
```

현재 Route 생성 로직에서는 `mainPlace`가 `TOURIST_SPOT`인지 검증한 뒤 저장한다.

### 해석

저장형 우회 대안이 최소 하나 이상 준비되어 있는 관광지의 범위를 나타낸다.

전국 관광지에 대한 서비스 커버리지를 의미하지 않는다.

전국 코스 제공은 실시간 생성 방식이 담당하며 이 지표와 별도로 본다.

---

## 6. 분산 대상 로컬 장소 수

### 정의

저장형 Route의 정류지로 한 번 이상 사용되고 있는 `LOCAL_PLACE`의 고유 개수이다.

### 계산

```text
RouteStop
→ Place와 placeId로 연결
→ Place.type = LOCAL_PLACE인 항목만 선택
→ placeId 중복 제거
→ 개수 계산
```

수식으로 표현하면 다음과 같다.

```text
분산 대상 로컬 장소 수
= COUNT(DISTINCT RouteStop.placeId)
  WHERE RouteStop.place.type = LOCAL_PLACE
```

같은 로컬 장소가 여러 Route에 등장하더라도 1곳으로 계산한다.

예시는 다음과 같다.

```text
Route A → 로컬 장소 1, 로컬 장소 2
Route B → 로컬 장소 1, 로컬 장소 3

분산 대상 로컬 장소
= 1, 2, 3
= 총 3곳
```

`RouteStop`에 연결된 장소라고 해서 무조건 로컬 장소로 간주하지 않고 실제 `Place.type`을 확인한다.

### 해석

저장형 우회 코스를 통해 관광객의 발걸음을 유도할 수 있도록 팀이 연결해 둔 **고유 로컬 장소의 공급 규모**를 의미한다.

실제 해당 장소에 방문한 사용자 수를 의미하지 않는다.

## 7. 관광지별 우회 용량

### 정의

각 기준 관광지가 얼마나 많은 저장형 우회 선택지를 가지고 있는지를 확인하기 위한 지표이다.

한 개의 단일 점수로 만들지 않고 다음 두 값을 함께 사용한다.

```text
관광지별 Route 수
평균 정류지 수
```

### 관광지별 Route 수

```text
관광지별 Route 수
= COUNT(Route.id)
  GROUP BY Route.mainPlaceId
```

### 평균 정류지 수

먼저 각 Route의 `RouteStop` 개수를 계산한다.

```text
Route별 정류지 수
= COUNT(RouteStop.id)
```

그 후 같은 `mainPlaceId`를 가진 Route들의 정류지 수 평균을 계산한다.

```text
관광지별 평균 정류지 수
= 해당 관광지의 전체 RouteStop 수
  / 해당 관광지의 Route 수
```

예시는 다음과 같다.

```text
관광지 A

Route 1 → 정류지 2곳
Route 2 → 정류지 3곳
Route 3 → 정류지 1곳

Route 수 = 3
평균 정류지 수 = (2 + 3 + 1) / 3 = 2
```

Route가 하나도 없는 관광지는 Route 기반 그룹 집계 결과에는 포함되지 않는다.

0으로 나누어 임의의 평균값을 생성하지 않는다.

### 활용

관광지별 값을 비교해 다음과 같은 경우를 확인하는 데 사용한다.

```text
Route 수가 적은 관광지
평균 정류지 수가 지나치게 적은 관광지
```

이를 통해 추가 큐레이션이 필요한 관광지를 찾을 수 있다.

현재 단계에서는 Route 수와 평균 정류지 수를 임의의 가중치로 합쳐 하나의 우회 용량 점수로 만들지 않는다.

## 8. 혼잡 감지 커버리지

### 정의

KTO 관광지 집중률 예측 대상 중 내부 `Place`와 연결할 수 있는 대상의 비율이다.

KTO 매칭 결과에는 다음 상태가 존재한다.

```text
MATCHED
ALIAS_MATCHED
UNMATCHED
AMBIGUOUS
```

`MATCHED`와 `ALIAS_MATCHED`만 매칭 성공으로 계산한다.

### 계산 기준

현재 `previewConcentrationMatching`의 결과를 기준으로 하면 다음과 같이 계산할 수 있다.

```text
매칭 성공 대상 수
= counts.matched
+ counts.aliasMatched
```

```text
전체 대상 수
= totalItems
```

```text
혼잡 감지 커버리지(%)
= 매칭 성공 대상 수 / 전체 대상 수 × 100
```

`UNMATCHED`와 `AMBIGUOUS`는 분자에 포함하지 않는다.

전체 대상 수가 0인 경우 0%라고 표시하지 않고 계산 불가 상태로 처리한다.

### 여러 지역을 합산하는 경우

여러 지역의 커버리지를 하나의 값으로 계산해야 하는 경우 지역별 비율의 단순 평균을 사용하지 않는다.

```text
전체 커버리지
= 모든 지역의 매칭 성공 대상 수 합
  / 모든 지역의 전체 대상 수 합
  × 100
```

### truncated 처리

집중률 preview 결과의 `truncated`가 `true`인 경우 전체 대상이 조회되지 않은 상태이므로 해당 값을 완전한 커버리지로 표시하지 않는다.

부분 데이터로 계산한 비율을 전체 커버리지처럼 노출하지 않는다.

### 현재 구현상 주의사항

현재 `Place`, `Congestion`, `ForecastPlaceAlias` 스키마에는 KTO의 전체 대상 목록과 `UNMATCHED`/`AMBIGUOUS` 상태를 지속적으로 저장하는 구조가 없다.

현재 `previewConcentrationMatching`은 외부 KTO API를 조회한 뒤 `totalItems` 및 각 매칭 상태를 계산한다.

따라서 이 지표는 다른 Route/Place 공급 지표와 달리 **현재 스키마만으로 DB 집계만 수행해서는 전체 분모를 재구성할 수 없다.**

관리자 `/analytics`를 반드시 DB-only 방식으로 구현해야 한다면 다음 중 하나의 방식에 대한 백엔드 결정이 필요하다.

```text
1. 집중률 매칭 집계 결과를 적재 시점에 별도로 저장한다.
또는
2. analytics 조회 시 기존 concentration matching preview 결과를 사용한다.
```

구현 방식이 결정되기 전에는 특정 시점의 숫자를 문서나 코드에 하드코딩하지 않는다.

## 9. 로컬 장소 큐레이션 완료율

### 정의

내부 `Place` 중 `LOCAL_PLACE`로 등록된 장소 가운데 저장형 우회 코스 큐레이션에 필요한 핵심 정보가 모두 입력된 장소의 비율이다.

현재 완료 여부 판단에는 다음 세 항목을 사용한다.

```text
태그
설명
추천 체류시간
```

운영시간은 관리자에서 별도로 미입력 현황을 확인하고 있지만 현재 `team-todo.md`에서 정의한 큐레이션 완료율의 필수 세 항목에는 포함하지 않는다.

### 전체 대상

```text
전체 큐레이션 대상 수
= COUNT(Place)
  WHERE Place.type = LOCAL_PLACE
```

### 완료 조건

다음 조건을 모두 만족하면 큐레이션 완료 장소로 계산한다.

```text
Place.type = LOCAL_PLACE

AND description 입력됨

AND recommendedDuration IS NOT NULL

AND PlaceTag가 1개 이상 존재
```

현재 장소 쓰기 API는 `recommendedDuration`이 입력되는 경우 양의 정수인지 검증하므로, 완료율 집계에서는 `null` 여부를 기준으로 입력 여부를 판단한다.

태그는 `PlaceTag` 관계가 하나 이상 존재하는지를 기준으로 한다.

### 계산

```text
로컬 장소 큐레이션 완료율(%)
= 큐레이션 완료 LOCAL_PLACE 수
  / 전체 LOCAL_PLACE 수
  × 100
```

전체 `LOCAL_PLACE`가 0개인 경우 0%라고 표시하지 않고 계산 불가 상태로 처리한다.

### 해석

이 값은 로컬 장소의 실제 방문 성과를 의미하지 않는다.

저장형 코스를 관리하기 위해 필요한 기본 정보가 어느 정도 준비되어 있는지를 나타내는 **데이터 품질 지표**이다.

## 10. 지표별 중복 처리 기준

| 지표             | 중복 처리                        |
| -------------- | ---------------------------- |
| 우회 코스 수        | 각 `Route.id`를 별도 1건으로 계산     |
| 코스 보유 관광지 수    | `mainPlaceId` 기준 중복 제거       |
| 분산 대상 로컬 장소 수  | `RouteStop.placeId` 기준 중복 제거 |
| 관광지별 우회 용량     | `mainPlaceId`별 그룹 집계         |
| 혼잡 감지 커버리지     | KTO 관광지 대상 단위의 매칭 결과 사용      |
| 로컬 장소 큐레이션 완료율 | `Place.id`별 1회 계산            |

같은 데이터를 여러 Route에서 사용하더라도 지표 목적에 따라 중복 제거 기준을 다르게 적용한다.

---

## 11. 관리자 화면 표시 기준

관리자 `/analytics` 화면에서는 현재 상태를 다음 두 범주로 구분해 보여주는 방향을 기준으로 한다.

### 전체 공급 현황

```text
우회 코스 수
코스 보유 관광지 수
분산 대상 로컬 장소 수
혼잡 감지 커버리지
로컬 장소 큐레이션 완료율
```

### 관광지별 상세 현황

```text
관광지명
Route 수
평균 정류지 수
```

지표 값은 현재 DB 및 매칭 상태를 기준으로 계산하며, 과거 값의 증가율이나 추세를 임의로 생성하지 않는다.

추세 분석이 필요하다면 별도의 snapshot 저장 구조를 먼저 설계한 뒤 도입한다.

---

## 12. 공모전 설명 시 해석 기준

현재 지표를 발표나 기능설명서에 사용할 때는 실제 관광객 행동을 측정한 것처럼 표현하지 않는다.

사용 가능한 표현의 예시는 다음과 같다.

```text
저장형 우회 코스를 N개 확보했다.

N개 관광지에 큐레이션된 우회 대안을 준비했다.

저장형 코스를 통해 N개의 고유 로컬 장소를 분산 대상으로 연결했다.

KTO 집중률 예측 대상 중 내부 장소와 연결 가능한 범위를 관리한다.

로컬 장소의 큐레이션 정보 완성도를 관리한다.
```

다음과 같은 표현은 실제 행동 데이터가 없으므로 사용하지 않는다.

```text
N명의 관광객을 분산시켰다.

로컬 장소 방문객이 N% 증가했다.

우회 코스 이용률은 N%이다.

N%의 사용자가 원 관광지로 복귀했다.

예상 분산 관광객은 N명이다.
```

현재 서비스의 강점은 행동 데이터를 수집하지 못해서 지표가 없는 것이 아니라, 사용자 위치와 방문 이력을 서버에 남기지 않도록 의도적으로 설계하면서도 **실제 관리 데이터에 기반한 분산 공급 역량을 제시한다는 점**에 있다.

---

## 13. 추후 확장

실제 사용자 행동 기반 지표가 공모전 심사 또는 서비스 운영에 반드시 필요해지는 경우 현재 구조에 임의로 추가하지 않는다.

먼저 위치정보 및 개인정보 영향 여부를 검토한 뒤 필요한 경우 익명 집계 방식의 도입을 별도로 논의한다.

검토 대상이 될 수 있는 지표는 다음과 같다.

```text
로컬 장소 도착률
코스 완료율
원 관광지 복귀율
```

해당 지표는 현재 데이터로 계산하지 않으며 현재 `/analytics`의 공급 지표에 포함하지 않는다.

---

## 14. 구현 전 확인 사항

현재 기준으로 확정된 지표는 다음 여섯 가지이다.

```text
1. 우회 코스 수
2. 코스 보유 관광지 수
3. 분산 대상 로컬 장소 수
4. 관광지별 우회 용량
5. 혼잡 감지 커버리지
6. 로컬 장소 큐레이션 완료율
```

이 중 Route, RouteStop, Place, PlaceTag 기반 지표는 현재 DB 구조만으로 계산할 수 있다.

혼잡 감지 커버리지는 현재 KTO 전체 대상 및 매칭 상태가 DB에 모두 보존되지 않으므로 `/analytics` 구현 전에 집계 데이터의 출처를 백엔드 담당자와 확정한다.

스키마 변경이 필요해지는 경우 데이터로직 담당이 임의로 변경하지 않고 현재 스키마 오너와 먼저 논의한다.
