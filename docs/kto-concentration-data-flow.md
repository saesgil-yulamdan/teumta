# KTO 관광지 집중률 예측 데이터 처리 기준

## 1. 문서 목적

한국관광공사 관광지 집중률 예측 데이터의 의미와 백엔드 처리 흐름을 정리하고, 외부 API 응답을 내부 `Place` 및 `Congestion` 데이터로 변환·저장하는 기준을 정의한다.

본 문서는 현재 백엔드에 구현된 KTO 관광지 집중률 예측 연동 및 적재 로직을 기준으로 작성한다.

---

## 2. 데이터 특성

KTO 관광지 집중률 예측 데이터는 향후 30일의 날짜별 관광지 집중률을 제공한다.

- 날짜 단위의 예측 데이터이다.
- 실시간 혼잡도 데이터가 아니다.
- 같은 날짜 내 시간대별 혼잡도를 제공하지 않는다.
- 미래 특정 시각의 혼잡도를 판단하는 데 사용하지 않는다.
- 여행 전 방문 예정일의 관광지 집중률을 확인하는 참고정보로 활용한다.

KTO 집중률 예측 데이터는 백엔드의 정기 적재 스케줄러를 통해 자동으로 갱신한다.

환경변수 `PREDICTION_INGEST_TARGETS`에 적재 대상 지역을 설정한 경우 스케줄러가 활성화된다.

예시는 다음과 같다.

```text
PREDICTION_INGEST_TARGETS=11:11110
```

여러 지역을 적재 대상으로 설정하는 경우 쉼표로 구분할 수 있다.

스케줄러는 다음 시점에 적재를 실행한다.

- 서버 기동 직후 1회
- 매일 KST 기준 지정된 시각 1회

일일 실행 시각은 `PREDICTION_INGEST_HOUR_KST` 환경변수로 설정하며, 기본값은 오전 5시이다.

현재 배포 서버에도 관련 환경변수가 설정되어 있어 KTO 집중률 예측 데이터가 매일 자동으로 적재된다.

수동 적재 스크립트는 자동 적재와 별도로 특정 지역의 재적재, 테스트 또는 수동 실행을 위한 보조 수단으로 사용한다.

---

## 3. KTO 응답 주요 필드

| KTO 필드 | 의미 | 내부 활용 |
|---|---|---|
| `baseYmd` | 예측 대상 날짜 | `Congestion.predictedFor`로 변환 |
| `areaCd` | 법정동 시도 코드 | Place 지역 매칭 |
| `areaNm` | 시도명 | 응답 확인용 |
| `signguCd` | 법정동 시군구 코드 | Place 지역 매칭 |
| `signguNm` | 시군구명 | 응답 확인용 |
| `tAtsNm` | 관광지명 | Place 이름 매칭 |
| `cnctrRate` | 관광지 집중률 원본값 | `Congestion.concentrationRate`에 저장 |

---

## 4. API 응답 항목 추출

KTO API의 `item` 값은 응답 건수에 따라 배열, 단일 객체 또는 빈 값으로 전달될 수 있다.

다음 기준에 따라 내부 배열로 변환한다.

| 응답 형태 | 처리 |
|---|---|
| `item`이 배열 | 배열을 그대로 사용 |
| `item`이 단일 객체 | 하나의 원소를 가진 배열로 변환 |
| `items`가 빈 문자열 | 빈 배열로 처리 |

응답 결과가 비어 있는 경우 임의 데이터를 생성하거나 저장하지 않는다.

---

## 5. 날짜 변환 기준

KTO의 `baseYmd`는 `yyyyMMdd` 형식의 한국 표준시 기준 달력 날짜로 해석한다.

예시는 다음과 같다.

```text
baseYmd: 20260806
한국 표준시: 2026-08-06 00:00 KST
UTC 저장값: 2026-08-05T15:00:00.000Z
```

UTC 저장값만 보면 날짜가 전날로 표시되지만, 실제 예측 대상 날짜는 한국 표준시 기준 2026년 8월 6일이다.

다음과 같은 값은 정상 날짜로 처리하지 않는다.

- `yyyyMMdd` 형식에 맞지 않는 날짜
- 실제로 존재하지 않는 날짜
- 변환할 수 없는 날짜 값

잘못된 날짜가 포함된 항목은 저장하지 않고 `skipped` 목록에 사유와 함께 집계한다.

---

## 6. 집중률 값 처리 기준

KTO의 `cnctrRate`는 문자열 또는 숫자 형태로 전달될 수 있다.

정상적인 숫자형 값은 원본 소수 정밀도를 유지해 `Congestion.concentrationRate`에 저장한다.

예시는 다음과 같다.

```text
"23.45" → 23.45
"7.05"  → 7.05
15.2    → 15.2
```

숫자로 변환할 수 없는 `cnctrRate`는 저장하지 않고 `skipped` 목록에 집계한다.

KTO 데이터는 공식적인 혼잡도 등급 임계값을 제공하지 않으므로, 집중률 값을 임의로 다음 단계로 변환하지 않는다.

- `RELAXED`
- `NORMAL`
- `CROWDED`
- `VERY_CROWDED`

KTO 집중률 데이터는 다음과 같이 저장한다.

```text
cnctrRate 원본값
→ concentrationRate에 저장
→ level은 null
→ score는 null
```

## 7. Place 매칭 기준

KTO 관광지 데이터는 지역 코드와 관광지명을 기준으로 내부 `Place` 데이터와 매칭한다.

### 7.1 지역 매칭

- KTO의 `areaCd`와 Place의 `lDongRegnCd`를 비교한다.
- KTO의 `signguCd`와 Place의 `lDongSignguCd`를 비교한다.
- 시군구 코드가 시도 코드를 포함한 전체 코드 형태로 전달되는 경우에도 동일 지역인지 확인한다.
- Place에 법정동 지역 코드가 없는 경우 자동 매칭하지 않는다.
- 관광지명이 같더라도 지역 코드가 다르면 매칭하지 않는다.

### 7.2 관광지명 매칭

KTO의 `tAtsNm`과 Place의 `name`을 정규화한 뒤 정확히 비교한다.

이름 정규화 범위는 다음과 같다.

- 문자열 앞뒤 공백 제거
- 연속된 공백을 하나의 공백으로 축소
- 괄호 앞뒤의 불필요한 공백 제거
- 유니코드 문자열을 NFC 형식으로 정규화

단어를 임의로 삭제하거나 부분 문자열 및 유사도 기반으로 매칭하지 않는다.

예를 들어 다음 이름은 서로 같은 장소로 자동 판단하지 않는다.

```text
경복궁
경복궁 야간개장
국립 경복궁
```

지역 코드와 정규화된 관광지명이 모두 일치해야 한다.

---

## 8. 매칭 결과 처리

Place 매칭 결과는 다음 세 가지 상태로 구분한다.

| 상태 | 조건 | 처리 |
|---|---|---|
| `MATCHED` | 지역과 이름이 일치하는 Place가 정확히 하나 | 해당 Place에 자동 저장 |
| `UNMATCHED` | 조건에 맞는 Place가 없음 | 저장하지 않고 목록에 집계 |
| `AMBIGUOUS` | 조건에 맞는 Place가 둘 이상 | 자동 저장하지 않고 후보 Place ID를 집계 |

`UNMATCHED` 및 `AMBIGUOUS` 데이터를 임의의 Place에 연결하지 않는다.

관광지명이 비어 있는 경우에도 `UNMATCHED`로 처리한다.

KTO 응답 데이터는 다음 기준으로 그룹화한 뒤 Place 매칭과 저장을 수행한다.

```text
areaCd + signguCd + tAtsNm
```

동일 관광지의 날짜별 예측 데이터를 하나의 그룹으로 처리한다.

---

## 9. Congestion 저장 기준

`MATCHED` 상태의 KTO 데이터만 `Congestion` 테이블에 저장한다.

| DB 필드 | 저장값 |
|---|---|
| `placeId` | 매칭된 Place ID |
| `type` | `PREDICTED` |
| `level` | `null` |
| `score` | `null` |
| `concentrationRate` | KTO `cnctrRate` 원본값 |
| `source` | `KTO_CONCENTRATION_FORECAST` |
| `measuredAt` | `null` |
| `predictedFor` | `baseYmd`를 KST 날짜 기준으로 변환한 값 |

코드에서는 `KTO_CONCENTRATION_FORECAST_SOURCE` 상수를 사용하지만, DB의 `source` 필드에는 실제 문자열 값인 `KTO_CONCENTRATION_FORECAST`가 저장된다.

전체 처리 흐름은 다음과 같다.

```text
KTO API 호출
→ 응답 항목 추출
→ 날짜 및 집중률 값 검증
→ areaCd, signguCd, tAtsNm 기준 그룹화
→ 지역 코드와 관광지명으로 Place 매칭
→ MATCHED 데이터만 Congestion 저장 형태로 변환
→ DB 저장
```

실시간 혼잡도인 `REALTIME` 데이터는 해당 KTO 예측 데이터 적재 서비스에서 처리하지 않는다.

## 10. 중복 및 갱신 기준

동일한 예측 데이터가 중복 저장되지 않도록 다음 조합에 고유 제약을 적용한다.

```text
placeId + source + predictedFor
```

KTO 데이터를 다시 적재할 때는 같은 장소와 같은 KTO source의 기존 데이터 중, 이번 API 응답이 반환한 날짜 범위에 포함되는 데이터만 삭제한 뒤 새 응답으로 교체한다.

```text
같은 placeId
+ type이 PREDICTED
+ 같은 KTO source
+ 새 응답의 predictedFor 날짜 범위
→ 기존 데이터 삭제
→ 새 응답 데이터 저장
```

다른 source에서 저장한 데이터는 삭제하지 않는다.

예를 들어 이번 응답이 2026년 8월 6일부터 2026년 9월 4일까지의 데이터를 반환했다면, 해당 장소의 동일 KTO source 데이터 중 같은 날짜 범위만 교체한다.

삭제와 저장 작업은 하나의 데이터베이스 트랜잭션으로 처리한다.

---

## 11. 저장 결과 집계

적재 결과는 다음 항목으로 구분해 반환한다.

| 결과 항목 | 의미 |
|---|---|
| `matchedPlaces` | 정상적으로 Place와 매칭된 관광지 수 |
| `inserted` | 새로 저장한 예측 데이터 수 |
| `deleted` | 재적재 과정에서 교체를 위해 삭제한 기존 데이터 수 |
| `unmatched` | 매칭되는 Place가 없는 관광지 목록 |
| `ambiguous` | 후보 Place가 둘 이상인 관광지와 후보 ID 목록 |
| `skipped` | 날짜 또는 집중률 값이 잘못되어 건너뛴 항목 |

`skipped` 항목에는 관광지명, 예측 대상 날짜 원본값 및 건너뛴 이유를 포함한다.

---

## 12. 수동 적재 방식

자동 정기 적재와 별도로, KTO 집중률 예측 데이터는 수동 적재 스크립트를 통해서도 저장할 수 있다.

```bash
npm run ingest:prediction -- --areaCd=<시도코드> --signguCd=<시군구코드> [--name=<관광지명>]
```

필수 입력값은 다음과 같다.

- `areaCd`
- `signguCd`

관광지명인 `name`은 선택적으로 입력할 수 있다.

예시는 다음과 같다.

```bash
npm run ingest:prediction -- --areaCd=11 --signguCd=11110 --name=경복궁
```

`areaCd` 또는 `signguCd`가 없으면 API 적재를 실행하지 않고 사용 방법을 출력한다.

수동 적재는 정기 적재를 대체하는 기본 방식이 아니라, 특정 지역의 수동 재적재나 테스트 등에 사용하는 보조 수단이다.

---

## 13. 예외 및 보안 처리

- API 응답이 비어 있으면 저장 작업을 수행하지 않는다.
- 잘못된 `baseYmd`는 저장하지 않고 `skipped`로 집계한다.
- 잘못된 `cnctrRate`는 저장하지 않고 `skipped`로 집계한다.
- `UNMATCHED` 데이터는 자동 저장하지 않는다.
- `AMBIGUOUS` 데이터는 자동 저장하지 않는다.
- 임의의 집중률 값이나 혼잡도 단계를 생성하지 않는다.
- API 키는 로그에 출력하지 않는다.
- API 키가 포함된 완성된 요청 URL을 로그에 출력하지 않는다.
- 외부 API 오류 메시지에 API 키, 요청 URL 및 원본 응답 본문을 포함하지 않는다.

공공데이터포털이 JSON 요청에 XML 형식의 오류 응답을 반환하는 경우에도 공통 HTTP 클라이언트에서 오류 유형을 구분해 처리한다.

결과 코드 `03`은 데이터가 없는 상태로 처리하며 정상적인 빈 결과로 정규화한다.

```text
resultCode = 03
→ 데이터 없음
→ 빈 목록으로 처리
```

다만 인증 실패, 요청 횟수 제한, 비정상 응답 등의 오류는 데이터 없음 상태로 처리하지 않는다.

즉 실제로 조회 결과가 없는 경우와 외부 API 호출 자체가 실패한 경우를 구분한다.

확인된 오류 유형은 다음과 같다.

- 데이터 없음
- 인증 오류
- 요청 횟수 제한 오류
- 정상적인 오류 봉투가 아닌 응답
- JSON 파싱 실패

## 14. 현재 구현 범위

현재 백엔드에 구현된 KTO 집중률 예측 관련 범위는 다음과 같다.

- KTO 관광지 집중률 예측 API 호출
- 응답 데이터 추출 및 변환
- 날짜와 집중률 값 검증
- 지역 코드와 관광지명을 이용한 Place 매칭
- `MATCHED`, `UNMATCHED`, `AMBIGUOUS` 구분
- `MATCHED` 데이터의 `Congestion` 저장
- 동일 source 및 날짜 범위 데이터 교체
- 일일 자동 적재 스케줄러
- 서버 기동 직후 자동 적재
- 수동 데이터 적재 스크립트
- 외부 API 오류 및 보안 처리

자동 적재 스케줄러는 `PREDICTION_INGEST_TARGETS`가 설정된 경우 활성화된다.

서버 기동 직후 1회 실행하며, 이후 `PREDICTION_INGEST_HOUR_KST`에 설정된 KST 기준 시각에 매일 실행한다.

`PREDICTION_INGEST_HOUR_KST`의 기본값은 오전 5시이다.

현재 배포 서버에서도 자동 적재가 활성화되어 있다.

### SK 실시간 혼잡도

SK 실시간 혼잡도는 KTO 예측 데이터와 달리 DB에 적재하지 않는 구조로 설계되어 있다.

외부 SK API의 현재 혼잡도 정보를 조회한 뒤 클라이언트에 전달하는 pass-through 방식으로 처리한다.

현재 다음 조회 API가 구현되어 있다.

```text
GET /api/congestion?poiId=<POI_ID>
```

SK 실시간 혼잡도 응답은 서버에서 5분 동안 캐시한다.

따라서 SK 실시간 혼잡도는 "DB 적재 기능이 아직 구현되지 않은 상태"가 아니라, 설계상 DB에 저장하지 않고 실시간 조회 결과를 사용하는 구조이다.

현재 구현되지 않았거나 별도 확인이 필요한 범위는 다음과 같다.

- KTO 집중률의 `CongestionLevel` 변환
- `UNMATCHED` 관광지의 자동 Place 생성
- `AMBIGUOUS` 데이터의 자동 후보 선택
- KTO 집중률의 사용자 화면 표시 기준
