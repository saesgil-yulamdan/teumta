# 혼잡도 판단 기준

혼잡 데이터 두 종류를 구분하고, 언제 우회 코스를 띄울지 정한다.
KTO 집중률 예측의 적재 규칙도 여기서 함께 관리한다.

---

## 1. 두 데이터의 역할

| | `PREDICTED` | `REALTIME` |
|---|---|---|
| 출처 | 한국관광공사 관광지 집중률 예측 | SK 퍼즐 장소 혼잡도 |
| 단위 | **날짜별**(향후 30일) | **현재 시점** |
| 쓰는 때 | 여행 전 날짜 고르기 | 여행 당일 |
| 저장 | DB 적재(§6) | 저장 안 함, 5분 캐시 pass-through |

**서로 대체하지 않는다.** 값의 범위·의미·산정 기준이 달라 직접 비교하거나 공통 threshold를 적용하지 않는다.

KTO로 하지 않는 것 — 같은 날짜 안의 시간대 비교, 특정 미래 시각 예측, 복귀 시점 혼잡도 판단.
SK로 하지 않는 것 — 미래 시점 예측.

---

## 2. 혼잡도 단계

| 단계 | 안내 문구 |
|---|---|
| `RELAXED` | 현재 비교적 여유로운 상태입니다. |
| `NORMAL` | 방문객이 있지만 이용 가능한 상태입니다. |
| `CROWDED` | 현재 혼잡하여 우회 코스를 확인할 수 있습니다. |
| `VERY_CROWDED` | 현재 매우 혼잡하여 우회 코스를 우선 추천합니다. |

이 단계는 **SK 실시간 데이터에만** 쓴다.

**KTO에는 등급을 매기지 않는다.** 공식 임계값이 없어 임의 등급은 근거 없는 판단이 된다.
원본값만 `Congestion.concentrationRate`에 저장하고 `level`·`score`는 `null`이다
(`Congestion.level`이 nullable인 이유). 화면에서도 등급 대신 중앙값 대비 상대 표현만 쓴다.

---

## 3. 여행 전 — 날짜별 집중률

방문 예정일의 예상 집중률을 보여주고, 상대적으로 낮은 날짜를 참고정보로 제안한다.
시간대 추천이나 당일 우회 판단에는 쓰지 않는다.

> 방문 예정일은 관광지 집중률이 높은 날로 예상됩니다.
> 다음 날은 상대적으로 낮을 것으로 예상됩니다.

---

## 4. 조회 실패 처리

| 실패 | 처리 |
|---|---|
| SK 실시간 조회 실패 | "현재 혼잡도를 확인할 수 없습니다." 안내. **KTO 값으로 대체하지 않는다.** 자동 우회 추천도 실행하지 않는다. KTO가 있으면 날짜 단위 참고정보로만 별도 표시 |
| KTO 조회 실패 | 날짜별 집중률을 제공하지 않는다. 실시간 판단에는 영향 없음 |
| 공통 | 임의의 집중률·혼잡도 값을 만들어 내지 않는다 |

---

## 5. 여행 당일 — 우회 코스 노출 기준 (확정)

**`CROWDED` 또는 `VERY_CROWDED`일 때 우회 코스를 강조한다.**
`RELAXED`·`NORMAL`에서는 혼잡을 이유로 우회를 앞세우지 않는다(사용자가 직접 열어보는 건 언제나 가능).

우회 코스를 추천 후보로 쓰려면 다음을 만족해야 한다.

1. 사용자가 30 / 60 / 90분 중 이용 가능 시간을 선택했다
2. 이동시간 + 체류시간 + 복귀시간의 합이 그 시간 이하다
3. 마지막 장소에서 원래 관광지로 복귀할 수 있다
4. TMAP 보행 경로 계산이 성공했다 — 실패한 코스는 후보에서 제외한다

**복귀 시점의 혼잡도는 조건에 넣지 않는다.** KTO는 날짜 단위라 특정 시각을 판단할 수 없다.
예상 복귀 시각은 `현재 시각 + 총 소요시간`이며, 그 시각의 혼잡 상태를 예측한 값이 아니다.

코스 구성·체류시간·순서 기준은 [route-data-rules.md](./route-data-rules.md)를 따른다.
**장소별 권장 체류시간 기준**은 아직 공식 근거가 없는 팀 합의값이다(§8 미결정).

## 6. KTO 집중률 적재 규칙

> 앱은 실시간 조회(`GET /api/concentration-forecast?contentId=`)를 쓰므로 이 적재 경로에 의존하지 않는다.
> 적재분은 내부 Place 기준 조회(3.4b)와 매칭 도구용이다.

### 스케줄러

`PREDICTION_INGEST_TARGETS`(예: `11:11110`, 쉼표로 복수)가 설정되면 활성화된다.
서버 기동 직후 1회 + 매일 `PREDICTION_INGEST_HOUR_KST`(기본 05시 KST) 1회 실행.
수동 재적재는 보조 수단이다.

```bash
npm run ingest:prediction -- --areaCd=11 --signguCd=11110 [--name=경복궁]
```

### Place 매칭

지역 코드(`areaCd`↔`lDongRegnCd`, `signguCd`↔`lDongSignguCd`)와 **정규화한 이름이 모두 정확히 일치**해야 한다.
정규화는 앞뒤 공백 제거·연속 공백 축소·괄호 주변 공백 정리·NFC까지만. **부분 문자열이나 유사도 매칭은 하지 않는다** —
"경복궁"과 "경복궁 야간개장"은 다른 장소다.

| 결과 | 조건 | 처리 |
|---|---|---|
| `MATCHED` | 후보 Place 정확히 1건 | 저장 |
| `UNMATCHED` | 후보 없음 | 저장하지 않고 집계 → 관리자 alias로 수동 연결 |
| `AMBIGUOUS` | 후보 2건 이상 | 저장하지 않고 후보 ID 집계 |

관리자가 등록한 alias(`ForecastPlaceAlias`)는 자동 매칭보다 우선한다.
`UNMATCHED`·`AMBIGUOUS`를 임의의 Place에 연결하지 않는다.

### 저장

`MATCHED`만 `Congestion`에 저장한다. `type=PREDICTED`, `source=KTO_CONCENTRATION_FORECAST`,
`level`·`score`·`measuredAt`은 `null`, `predictedFor`는 `baseYmd`를 **KST 달력 날짜**로 해석한 값이다
(UTC 저장값은 전날로 보이지만 정상).

재적재는 `placeId + source + predictedFor` 유니크 제약 위에서, **이번 응답이 반환한 날짜 범위만**
삭제 후 교체한다(한 트랜잭션). 다른 source의 데이터는 건드리지 않는다.

값을 숫자로 변환할 수 없거나 날짜 형식이 잘못된 항목은 저장하지 않고 `skipped`에 사유와 함께 집계한다.

### 외부 API 예외

`resultCode=03`은 **데이터 없음**이라 빈 목록으로 정규화한다. 인증 실패·호출 한도 초과·비정상 응답·JSON 파싱
실패는 데이터 없음으로 뭉개지 않고 오류로 구분한다(포털이 JSON 요청에 XML 오류를 주는 경우 포함).

API 키, 키가 포함된 요청 URL, 외부 응답 원문은 **로그와 오류 메시지에 남기지 않는다.**

## 7. TMAP 사용 범위

경로 계산은 **장소 고정 좌표끼리만** 수행한다(`Place ↔ Place`, 또는 실시간 코스의 외부 장소 좌표).
사용자 GPS는 서버 요청에도 TMAP 호출에도 포함하지 않는다([location-privacy.md](./location-privacy.md)).

| Mobile | Backend |
|---|---|
| 현재 GPS 처리 · 도착 판정 · 진행 상태 · 이탈 판정 | 후보 조회 · 필터링 · 이동시간/거리 계산 · 총 소요시간 · 예상 복귀 시각 |

---

## 8. 미결정

- 장소별 권장 체류시간 기준 — 현재 분류코드별 기본값(문화시설 40 / 쇼핑 30 / 음식점 40분)은 **팀 합의값**이며 공식 통계가 아니다
- SK 원본 응답 → `CongestionLevel` 세부 mapping 임계값
- 코스 소요시간에 별도 여유시간을 둘지 여부
- 요일별 운영시간·휴무일 데이터 확보 방식(현재 스키마는 단일 운영시간만)
