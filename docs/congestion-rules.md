# 혼잡도 판단 기준 초안

## 1. 문서 목적

틈타 서비스에서 여행 전 확인하는 날짜별 예상 관광지 집중률과 여행 당일 확인하는 실시간 장소 혼잡도를 구분하고, 각 데이터의 활용 기준을 정의한다.

또한 실시간 혼잡도가 높은 경우 저장된 Route를 활용해 우회 코스를 추천하고, TMAP으로 실제 이동시간과 예상 복귀 시각을 계산하는 초기 기준을 정리한다.

본 문서는 현재 백엔드 구조와 외부 API의 데이터 특성을 기준으로 작성하며, 현재 구현된 KTO 관광지 집중률 예측 데이터 처리 및 SK 실시간 장소 혼잡도 변환 로직을 반영한다.

추천 로직, Route ranking 및 예외 처리 정책이 변경되는 경우 해당 기준도 함께 수정한다.

## 2. 혼잡도 데이터 구분

백엔드의 `CongestionType` 구조와 동일하게 혼잡도 데이터를 두 종류로 구분한다.

| 구분          | 의미                   | 데이터 소스                | 주요 활용 시점 |
| ----------- | -------------------- | --------------------- | -------- |
| `PREDICTED` | 특정 미래 날짜의 예상 관광지 집중률 | 한국관광공사 관광지 집중률 예측 데이터 | 여행 전     |
| `REALTIME`  | 현재 시점의 장소 혼잡도        | SK 장소 혼잡도 데이터         | 여행 당일    |

### PREDICTED

`PREDICTED`는 특정 미래 시각이나 시간대의 예상 혼잡도가 아니라, 특정 미래 날짜의 예상 관광지 집중률을 의미한다.

한국관광공사 관광지 집중률 예측 데이터를 기반으로 방문 예정일의 관광지 집중 수준을 제공한다.

현재 사용하는 KTO 데이터는 특정 시각이나 시간대별 미래 혼잡도를 제공하는 데이터가 아니므로 다음 용도로는 사용하지 않는다.

* 같은 날짜 내 시간대별 혼잡도 비교
* 특정 미래 시각의 혼잡도 예측
* 복귀 예정 시점의 혼잡도 예측

### REALTIME

`REALTIME`은 현재 시점에 측정된 장소 혼잡도를 의미한다.

SK 장소 혼잡도 데이터를 기반으로 여행 당일 현재 관광지의 혼잡 상태를 판단한다.

REALTIME 데이터는 현재 혼잡 상태를 판단하는 데 사용하며, 미래 특정 시점의 혼잡도를 예측하는 값으로 사용하지 않는다.

현재 SK 실시간 혼잡도는 DB에 별도로 적재하지 않고 외부 API 조회 결과를 내부 공통 형식으로 변환하여 전달하는 pass-through 방식으로 처리한다.

백엔드에서는 다음 조회 API를 제공한다.

```text
GET /api/congestion?poiId=<POI_ID>
```

실시간 혼잡도 응답은 서버에서 5분 동안 캐시한다.

## 3. 혼잡도 단계

백엔드의 `CongestionLevel` 구조와 동일하게 다음 네 단계를 사용한다.

| 단계             | 의미    | 사용자 안내 예시                   |
| -------------- | ----- | --------------------------- |
| `RELAXED`      | 여유    | 현재 비교적 여유로운 상태입니다.          |
| `NORMAL`       | 보통    | 방문객이 있지만 이용 가능한 상태입니다.      |
| `CROWDED`      | 혼잡    | 현재 혼잡하여 우회 코스를 확인할 수 있습니다.  |
| `VERY_CROWDED` | 매우 혼잡 | 현재 매우 혼잡하여 우회 코스를 우선 추천합니다. |

위 사용자 안내 문구와 혼잡도 단계는 현재 혼잡 상태를 보여주는 `REALTIME` 데이터를 중심으로 사용한다.

백엔드의 `Congestion.level` 필드는 nullable로 정의되어 있으므로 모든 외부 데이터에 반드시 `CongestionLevel`을 부여하지 않는다.

### KTO 데이터

KTO 관광지 집중률 예측 데이터는 공식적인 혼잡도 등급 임계값을 제공하지 않으므로 공식 기준 없이 임의로 `RELAXED`, `NORMAL`, `CROWDED`, `VERY_CROWDED` 단계를 생성하지 않는다.

KTO 데이터의 원본 집중률 값은 `Congestion.concentrationRate`에 저장하고 `level`과 `score`는 null로 저장한다.

```text
KTO 원본 concentrationRate
→ concentrationRate에 원본값 저장
→ level = null
→ score = null
```

### SK 데이터

SK 장소 혼잡도 데이터는 DB에 별도로 적재하지 않고 실시간 조회 결과를 사용하는 구조이다.

현재 백엔드의 SK 실시간 혼잡도 mapper에서는 원본 응답의 `congestionLevel`을 다음과 같이 내부 `CongestionLevel`로 변환한다.

| SK `congestionLevel` | 내부 `CongestionLevel` |
| -------------------- | -------------------- |
| `1`                  | `RELAXED`            |
| `2`                  | `NORMAL`             |
| `3`                  | `CROWDED`            |
| `4`                  | `VERY_CROWDED`       |

SK 응답은 다음 기준에 따라 내부 공통 혼잡도 데이터로 변환한다.

```text
SK 원본 데이터
→ rltm 배열에서 실시간 항목 선택
→ congestionLevel을 CongestionLevel로 변환
→ type = REALTIME
→ level = 변환된 CongestionLevel
→ score = null
→ source = SK_PUZZLE
→ measuredAt = SK datetime 변환값
→ predictedFor = null
→ 클라이언트에 전달
```

SK 응답의 `rltm` 배열에서는 `type=1`인 항목을 실시간 혼잡도 항목으로 우선 선택한다.

현재 구현에서는 `type=1`인 항목이 존재하지 않는 경우 `rltm` 배열의 첫 번째 항목을 fallback으로 사용한다.

`rltm` 배열 자체가 비어 있는 경우에는 실시간 혼잡도 항목이 없는 것으로 판단하여 외부 API 응답 오류로 처리한다.

현재 구현의 fallback 동작을 최종 정책으로 유지할지는 별도로 확인한다.

SK 원본 응답의 `congestion` 값은 내부 공통 점수로 정규화할 기준이 현재 정의되어 있지 않으므로 `score`에는 반영하지 않고 `null`로 처리한다.

SK 응답의 `datetime`은 KST 기준 날짜·시간 값으로 해석하여 `measuredAt`으로 변환한다.

현재 mapper는 12~14자리 숫자 형식의 값을 허용하며, 필요한 경우 14자리 형식으로 맞춘 뒤 KST(`+09:00`) 기준 `Date`로 변환한다.

유효한 형식으로 변환할 수 없는 경우 `measuredAt`은 `null`로 처리한다.

`congestionLevel`이 `1~4` 범위에 해당하지 않는 경우 임의의 기본 혼잡도 단계를 부여하지 않고 외부 API 응답 오류로 처리한다.

KTO 관광지 집중률과 SK 장소 혼잡도의 원본 데이터는 값의 범위, 의미 및 산정 기준이 서로 다르므로 직접 비교하지 않는다.

또한 두 데이터 소스에 동일한 점수 구간이나 공통 threshold를 적용하지 않는다.

추후 KTO 데이터에 `CongestionLevel`을 적용할 필요가 생기는 경우에도 KTO 데이터의 값 범위와 분포를 확인하고 팀에서 별도의 기준을 확정한 뒤 적용 여부를 검토한다.

## 4. 여행 전 예상 관광지 집중률 활용

한국관광공사 관광지 집중률 예측 데이터를 사용한다.

* 방문 예정일의 예상 관광지 집중률을 확인한다.
* 향후 날짜별 예상 관광지 집중률을 비교한다.
* 상대적으로 집중률이 낮은 날짜를 여행 전 참고정보로 제공할 수 있다.
* 같은 날짜 내 시간대별 혼잡도 비교에는 사용하지 않는다.
* 특정 시간대의 방문을 추천하는 용도로 사용하지 않는다.
* 여행 당일의 현재 실시간 혼잡도를 판단하는 값으로 사용하지 않는다.
* 실시간 우회 코스 추천 여부를 결정하는 값으로 사용하지 않는다.

사용자 안내 예시는 다음과 같다.

```text
방문 예정일은 관광지 집중률이 높은 날로 예상됩니다.

다음 날은 상대적으로 관광지 집중률이 낮을 것으로 예상됩니다.
```

KTO 데이터는 날짜 단위의 여행 전 참고정보로 사용한다.

## 5. 여행 당일 실시간 혼잡도 판단

SK 장소 혼잡도 데이터를 사용한다.

* 현재 관광지의 실시간 혼잡 상태를 확인한다.
* SK 데이터는 현재 시점의 혼잡 상태 판단에 사용한다.
* 미래 복귀 예정 시점의 혼잡도를 판단하는 값으로 사용하지 않는다.
* SK `congestionLevel`은 현재 백엔드 mapping 기준에 따라 내부 `CongestionLevel`로 변환한다.

  * `1` → `RELAXED`
  * `2` → `NORMAL`
  * `3` → `CROWDED`
  * `4` → `VERY_CROWDED`
* SK 원본 `congestion` 값은 공통 점수로 변환하지 않으며 `score`는 `null`로 처리한다.
* SK 응답의 `datetime`은 실시간 혼잡도 측정 시각인 `measuredAt`으로 변환한다.
* 실시간 데이터이므로 `predictedFor`는 `null`로 처리한다.

MVP에서는 SK 데이터가 `CROWDED` 또는 `VERY_CROWDED` 수준으로 판단되는 경우 우회 코스를 노출하는 방향을 기준으로 한다.

`RELAXED` 또는 `NORMAL`인 경우에는 혼잡으로 인한 자동 우회 코스를 우선 노출하지 않는다.

### 실시간 혼잡도 조회 실패

SK 실시간 혼잡도 조회에 실패한 경우 KTO 관광지 집중률 예측 데이터를 REALTIME 혼잡도의 대체값으로 사용하지 않는다.

KTO와 SK 데이터는 의미와 시간 단위가 다르기 때문에 KTO 예측값으로 현재 혼잡 상태를 판단하거나 자동 우회 코스 추천 여부를 결정하지 않는다.

실시간 데이터 조회에 실패한 경우 다음과 같이 처리한다.

* 사용자에게 `현재 혼잡도를 확인할 수 없습니다.`라고 안내한다.
* 실시간 혼잡도를 기반으로 한 자동 우회 코스 추천은 실행하지 않는다.
* KTO 데이터가 존재하는 경우 날짜 단위 참고정보로 별도 표시할 수 있다.

예시는 다음과 같다.

```text
현재 혼잡도를 확인할 수 없습니다.

오늘은 관광지 집중률이 높은 날로 예상됩니다.
```

두 번째 문장은 현재 실시간 혼잡도가 아니라 날짜 단위 예상 정보임을 사용자에게 명확히 표시한다.

## 6. Route 추천 방식

MVP에서는 후보 Place들을 요청 시점마다 조합해 새로운 Route를 동적으로 생성하지 않고, 미리 등록된 Route 후보를 활용하는 방식을 기준으로 한다.

저장된 Route 중 다음 조건을 기반으로 후보를 필터링하고 우선순위를 계산한다.

* 사용자가 선택한 이용 가능 시간
* Route에 포함된 장소의 이용 가능 여부
* 예상 코스 소요시간
* TMAP 재계산 결과
* 원래 관광지로 복귀 가능한지 여부

Route의 장소 구성과 방문 순서는 미리 저장한다.

Route에 저장된 예상 이동시간과 거리는 후보 Route를 1차로 확인하는 데 사용할 수 있으며, 사용자에게 제공할 최종 이동시간과 예상 복귀 시각은 요청 시 TMAP 데이터를 이용해 다시 계산한다.

MVP 추천 흐름은 다음과 같다.

```text
현재 관광지의 실시간 혼잡도 확인
→ 사용자가 이용 가능한 시간 선택
→ 저장된 Route 후보 조회
→ 장소 이용 가능 여부 확인
→ 저장된 예상 소요시간 기준 후보 확인
→ TMAP으로 Place 간 실제 이동시간 재계산
→ 전체 코스 소요시간 계산
→ 예상 복귀 시각 계산
→ 조건에 맞는 Route 필터링 및 ranking
→ 최종 우회 코스 추천
```

동적 Route 생성 방식의 도입 여부는 MVP 이후 별도로 검토한다.

## 7. 우회 코스 추천 조건

MVP에서는 다음 조건을 기준으로 우회 코스 추천 후보를 판단한다.

1. 현재 관광지의 실시간 혼잡도가 우회 추천이 필요한 수준으로 판단된다.
2. 사용자가 우회 코스를 이용할 수 있는 시간을 선택했다.
3. Route에 포함된 장소의 운영시간 정보가 존재하는 경우 예상 방문 시각이 운영시간 범위 안에 포함된다.
4. 이동시간과 권장 체류시간을 포함한 전체 코스 소요시간이 사용자가 선택한 시간 이하이다.
5. 마지막 장소 방문 후 원래 관광지로 복귀할 수 있다.
6. TMAP을 통한 장소 간 이동시간 및 복귀시간 계산이 가능하다.

현재 `Place`에는 `openingTime`과 `closingTime`이 저장되어 있으나, 요일별 운영시간, 정기 휴무일 및 임시 휴무 정보를 저장하는 구조는 없다.

따라서 장소의 정확한 실시간 운영 여부를 판단하는 방식은 추가 데이터 확보 여부에 따라 보완한다.

### 복귀 예정 시점 혼잡도

다음 조건은 MVP 필수 추천 조건에서 제외한다.

```text
복귀 예정 시점의 예상 혼잡도가 현재보다 낮다.
```

해당 조건을 판단하려면 미래 특정 시간대의 혼잡도를 확인할 수 있는 데이터가 필요하다.

현재 KTO 관광지 집중률 데이터는 날짜별 예상 집중률이므로 복귀 예정 시점의 혼잡도 판단에 사용할 수 없다.

현재 사용 중인 SK 실시간 혼잡도 역시 현재 시점의 혼잡 상태 판단에 사용하며, 현재 구현에서는 복귀 예정 시점의 혼잡도 판단에 사용하지 않는다.

향후 미래 특정 시점의 혼잡도 데이터를 서비스에서 활용할 수 있는지는 별도로 검토한다.

## 8. 코스 시간 구분 및 소요시간 계산

사용자가 선택한 이용 가능 시간을 기준으로 Route 후보를 필터링한다.

코스 총 소요시간에는 다음 항목을 포함한다.

* 원래 관광지에서 첫 번째 로컬 장소까지의 이동시간
* 각 로컬 장소의 권장 체류시간
* 로컬 장소 사이의 이동시간
* 마지막 로컬 장소에서 원래 관광지까지의 복귀시간
* 필요한 경우 별도로 설정한 여유시간

전체 코스 소요시간은 다음과 같이 계산한다.

```text
전체 코스 소요시간
= 장소 간 총 이동시간
+ 장소별 총 권장 체류시간
+ 설정된 여유시간
```

전체 코스 소요시간이 사용자가 선택한 이용 가능 시간 이하인 Route만 추천 후보에 포함한다.

예시는 다음과 같다.

```text
사용자 선택 시간: 60분

예상 총 소요시간 55분
→ 추천 가능

예상 총 소요시간 68분
→ 추천 제외
```

---

## 9. 예상 복귀 시각 계산

예상 복귀 시각은 현재 시각에 Route의 전체 예상 소요시간을 더해 계산한다.

```text
예상 복귀 시각
= 현재 시각
+ 장소 간 총 이동시간
+ 장소별 총 권장 체류시간
+ 설정된 여유시간
```

예상 복귀 시각은 사용자가 우회 코스를 완료하고 원래 관광지로 돌아오는 예상 시간을 의미한다.

복귀 예정 시점의 미래 혼잡도는 현재 MVP 계산에 포함하지 않는다.

따라서 예상 복귀 시각은 시간 계산 결과이며 해당 시각의 혼잡 상태를 예측한 결과가 아니다.

---

## 10. TMAP 사용 범위

TMAP 경로 계산은 Route에 포함된 관광지 및 로컬 장소의 고정 좌표를 기준으로 수행한다.

Backend에서 TMAP을 호출할 때는 데이터베이스의 `Place.latitude`, `Place.longitude`에 저장된 장소 좌표를 이용해 Place와 Place 사이의 이동시간과 거리를 계산한다.

예시는 다음과 같다.

```text
원래 관광지 → Place A
Place A → Place B
Place B → 원래 관광지
```

사용자의 현재 GPS 좌표는 Backend에서 수행하는 Place 간 Route 계산의 기준 좌표로 사용하지 않는다.

Route 시작 지점 역시 데이터베이스에 저장된 현재 관광지의 좌표를 기준으로 계산한다.

### Mobile 역할

* 사용자의 현재 GPS 정보 처리
* 장소 도착 여부 판단
* 코스 진행 상태 관리
* Route 이탈 여부 판단

### Backend 역할

* 저장된 Route 후보 조회
* Route 조건 필터링
* Route ranking
* Place 간 이동시간 및 거리 계산
* 전체 코스 소요시간 계산
* 예상 복귀 시각 계산

GPS를 이용한 도착 및 코스 진행 여부 판단은 Mobile에서 처리한다.

---

## 11. Route 필터링 및 ranking 기준

### 1차 필터링

* 사용자가 선택한 이용 가능 시간 조건에 맞는지 확인한다.
* Route에 포함된 장소의 운영시간 정보가 있는 경우 예상 방문 가능 여부를 확인한다.
* 저장된 예상 소요시간을 기준으로 후보 Route를 확인한다.
* 현재 관광지를 기준으로 등록된 우회 Route인지 확인한다.

### 최종 필터링

* TMAP 경로 계산에 성공했는지 확인한다.
* TMAP으로 다시 계산한 전체 소요시간이 사용자가 선택한 시간 이하인지 확인한다.
* 마지막 장소 방문 후 원래 관광지로 복귀할 수 있는지 확인한다.
* 이용이 불가능하다고 확인된 장소가 포함된 경우 해당 Route를 제외한다.

### 초기 ranking 기준

MVP에서는 다음 항목을 Route ranking 후보 기준으로 검토한다.

* 사용자가 선택한 시간과 실제 코스 소요시간의 적합도
* 총 이동시간
* 총 이동거리
* Route 데이터의 유효성

세부 ranking 우선순위와 가중치는 팀 논의를 통해 확정한다.

Route에 포함된 개별 장소의 실시간 혼잡도를 ranking에 활용할 수 있는지는 SK 데이터 제공 장소와 내부 `Place` 간 매칭 가능 범위를 확인한 후 결정한다.

## 12. 예외 처리

### SK 실시간 혼잡도 조회 실패

* KTO 예측 데이터를 REALTIME 혼잡도의 대체값으로 사용하지 않는다.
* 사용자에게 현재 혼잡도를 확인할 수 없음을 안내한다.
* 실시간 혼잡도를 기준으로 한 자동 우회 코스 추천은 실행하지 않는다.
* KTO 데이터는 날짜 단위 참고정보로만 별도 표시할 수 있다.

### SK 응답에 실시간 항목이 없는 경우

현재 mapper는 `rltm` 배열에서 `type=1`인 항목을 우선 선택한다.

`type=1`인 항목이 없는 경우 현재 구현에서는 배열의 첫 번째 항목을 fallback으로 사용한다.

`rltm` 배열 자체가 비어 있는 경우 외부 API 응답 오류로 처리한다.

해당 fallback을 최종 정책으로 유지할지는 팀에서 별도로 확인한다.

### SK 혼잡도 단계가 유효하지 않은 경우

* `congestionLevel`이 `1~4` 범위에 해당하지 않는 경우 임의의 `CongestionLevel`을 생성하지 않는다.
* 알 수 없는 혼잡도 단계는 외부 API 응답 오류로 처리한다.

### SK 측정 시각을 변환할 수 없는 경우

* 유효한 형식의 `datetime`이 아닌 경우 `measuredAt`을 `null`로 처리한다.
* 임의의 현재 시각을 측정 시각으로 생성하지 않는다.

### KTO 관광지 집중률 조회 실패

* 여행 전 날짜별 예상 집중률 정보를 제공하지 않는다.
* REALTIME 혼잡도 판단에는 영향을 주지 않는다.
* 임의의 집중률 또는 혼잡도 값을 생성하지 않는다.

### TMAP 경로 계산 실패

* 해당 Route의 실제 이동시간을 계산할 수 없는 것으로 처리한다.
* 이동시간 검증이 완료되지 않은 Route는 추천 후보에서 제외한다.
* 다른 Route 후보가 존재하는 경우 다음 후보를 확인한다.

### 장소 운영 여부 확인

* 저장된 `openingTime`, `closingTime`을 기준으로 확인 가능한 범위에서 이용 가능 여부를 판단한다.
* 운영시간 정보가 없는 장소의 추천 정책은 별도로 결정한다.
* 요일별 휴무 또는 임시 휴무는 현재 저장 구조만으로 완전히 판단할 수 없다.

### 선택 시간 내 이용 가능한 Route가 없는 경우

* 제한시간 안에 복귀할 수 없는 Route는 추천 후보에서 제외한다.
* 사용자에게 선택한 시간 내 이용 가능한 우회 코스가 없음을 안내한다.
* 필요한 경우 더 긴 시간 조건을 선택할 수 있도록 안내할 수 있다.

### 이용 가능한 대안 Route가 없는 경우

* 사용자에게 현재 제공 가능한 우회 코스가 없음을 안내한다.
* 임의로 새로운 장소 또는 Route를 생성하지 않는다.

## 13. 추후 확인 및 결정 사항

* SK 원본 `congestion` 값의 범위, 의미 및 서비스 내 활용 여부
* SK `rltm` 배열에 `type=1` 항목이 없는 경우 현재 fallback 처리를 유지할지 여부
* SK 데이터 제공 가능 장소와 내부 `Place` 간 매칭 범위
* 미래 특정 시점의 혼잡도 데이터 확보 및 활용 여부
* 복귀 예정 시점의 혼잡도 판단 기능 도입 여부
* `CROWDED` 단계부터 자동 우회 코스를 노출하는 것이 적절한지 여부
* KTO 집중률의 사용자 화면 표시 기준
* KTO 집중률의 날짜별 비교 기준
* KTO 데이터에 `CongestionLevel` mapping을 추가할지 여부
* Route ranking의 세부 우선순위 및 가중치
* 장소별 권장 체류시간 기준
* 코스 소요시간 계산에 적용할 여유시간 기준
* 요일별 영업시간 및 휴무일 데이터 확보 방식
* 운영시간을 확인할 수 없는 장소의 추천 정책
* 실시간 혼잡도 조회 실패 시 사용자가 직접 Route를 조회할 수 있도록 할지 여부
* 동적 Route 생성 기능의 MVP 이후 도입 여부
